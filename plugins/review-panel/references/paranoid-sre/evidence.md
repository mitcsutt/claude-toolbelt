|---|---|---|---|
| SR1 | 92% of catastrophic failures in 198 user-reported failures came from incorrect handling of non-fatal errors. Most could have been prevented by simple testing of error-handling code. Almost all reproduce on ≤3 nodes, and the order of inputs matters. | R12 F1 (Yuan et al., OSDI'14; ;login: Feb 2015) | high; 58%/35% split and "77% unit-testable" UNVERIFIED (secondary only) |
| SR2 | Crash-consistency: 60 vulnerabilities across 11 widely used systems. Correctness "is highly dependent on subtle behaviors of the underlying file system". | R12 F2 (Pillai et al., OSDI'14) | high |
| SR3 | Retries are "one of the most common failure-sustaining mechanisms" in metastable failures (worked example: 560 QPS sustained after a 10 s blip). Remedy: a retry budget, or no retries. Metastable failures are "universally observed" (22 failures, 11 organisations). | R12 F3 (Bronson et al., HotOS'21; Huang et al., OSDI'22) | high |
| SR4 | "roughly 70% of outages are due to changes in a live system". The prescribed practices are progressive rollout, fast detection and safe rollback. | R12 F4 (Google SRE book, Introduction) | medium (vendor) |
| SR5 | Gray failure: "the system's failure detectors may not notice problems even when applications are afflicted by them". A check that proves the process or port is alive is evidence of liveness, not health. | R12 F6 (Huang et al., HotOS'17) | high |
| SR6 | Azure incidents: software bugs ≈40%, and within them error handling 31%, data-format change 21%, timing 13%, "only a small number of configuration bugs". So rank error handling and data format above config typos, and don't claim config causes most outages. | R12 F7, F10 (Liu et al., HotOS'19 via acolyer 2019-06-21; Gunawi et al., SoCC'16 via blog) | medium; percentages UNVERIFIED |
| SR7 | Timeout bugs are mostly misused timeout values or missing timeouts. | R12 F8 (Dai et al., IC2E'18 slides; TFix+ arXiv 2110.04101) | medium; percentages UNVERIFIED |
| SR8 | "time-zone-related mistakes are the largest contributing factor to date/time bugs" (151 bugs). | R12 F9 (Tiwari et al., MSR'25 abstract) | medium |
| SR9 | Retries can worsen overload; "retry at a single point in the stack"; "APIs with side effects aren't safe to retry unless they provide idempotency"; jitter spreads retries out. | R12 F11 (AWS Builders' Library, 2019-12-05) | high |
| SR10 | Default timeouts: Requests "do not time out unless a timeout value is set explicitly". undici (Node `fetch`) `headersTimeout` and `bodyTimeout` both "Default: `300e3`" (5 min each). | R12 F12 (requests docs; undici `docs/docs/api/Client.md`) | high; undici value volatile |
| SR11 | `set -e` is ignored in an `if`/`while` test, in `&&`/`||` lists except after the final operator, and in all but the last command of a pipeline. A function or compound command called in such a context runs its whole body with `-e` off. `local x=$(cmd)` masks `cmd`'s status. | R12 F13 (Bash manual, The Set Builtin; BashFAQ/105; ShellCheck SC2155) | high |
| SR12 | rename(2) replaces newpath atomically for observers. fsync(2) on the file doesn't persist the directory entry; "an explicit fsync() on a file descriptor for the directory is also needed". | R12 F14 (man7 rename(2), fsync(2)) | high |
| SR13 | Compose `restart` acts "on container termination". A restart policy applies only after a successful start (up ≥10 s) and is ignored after a manual stop until the daemon restarts. HEALTHCHECK only emits a `health_status` event (defaults: interval 30s, timeout 30s, retries 3, start-period 0s). "Compose does not wait until a container is 'ready', only until it's running" unless `condition: service_healthy`. `depends_on.restart: true` excludes restarts by the runtime. "The engine doesn't restart unhealthy containers" is an inference for the standalone engine and Compose: no doc sentence says so (Swarm services do replace unhealthy tasks). | R12 F15 (docs.docker.com: Dockerfile HEALTHCHECK, start-containers-automatically, compose startup-order, compose services) | high for quotes, medium-high for the inference; volatile |
| SR14 | systemd doesn't restart a service whose death came from a systemd stop or restart. `RestartSec=` defaults to 100ms. Units that reach the start limit "are not attempted to be restarted anymore". `DefaultStartLimitIntervalSec=` defaults to 10s and `DefaultStartLimitBurst=` to 5. | R12 F16 (freedesktop systemd.service(5), systemd.unit(5), systemd-system.conf(5)); re-checked locally 2026-11-19, systemd 255.4-1ubuntu8.18 `man 5 systemd-system.conf` | high; defaults volatile (distro and `system.conf` can override) |
| SR15 | flock(2) releases the lock "when all such file descriptors have been closed", so a crash frees it, but a child that inherits the fd holds it. `time.monotonic()` "is not affected by system clock updates". Debian cron: jobs in a skipped-forward hour "will be run soon after the change", and jobs in a repeated hour (clock back <3 h) "will not be re-run"; wildcard jobs follow the new time. Cron sets SHELL, LOGNAME and HOME and a minimal PATH (`/usr/bin:/bin`); on Debian, pam_env adds `/etc/environment`. No login profile is read. | R12 F17 (man7 flock(2); Debian crontab(5); docs.python.org time; Debian cron(8)); cron(8) DST text re-checked locally 2026-11-19, cron 3.0pl1-184ubuntu2 | high; cron behaviour is Debian/Vixie-specific |
| SR16 | GNU ln: "The default is to treat a destination that is a symlink to a directory just like a directory". So a second `ln -s target link` creates `link/<name>` inside the old target instead of repointing `link`. Fix: `ln -sfn` (portable: GNU and FreeBSD; `-T` is GNU-only). | R12 §3 S1, §5 P1 (GNU coreutils ln-invocation) | high for GNU; FreeBSD ln also dereferences by default; macOS UNVERIFIED |
| SR17 | A failed `CREATE INDEX CONCURRENTLY` leaves an "invalid" index ("drop the index and try again"). `IF NOT EXISTS` gives "no guarantee that the existing index is anything like the one that would have been created". So re-running the migration silently keeps the INVALID index. | R12 F30 (postgresql.org/docs/current sql-createindex) | high for quotes; the re-run consequence is an inference, high |
| SR18 | Models don't self-correct without external feedback, tool verification works, and empirical runs find failures nobody predicted by reading. This is why the checks that only running settles go under Coverage with a command. Fault injection in this lens is deferred until it has OS confinement, and whether it would find more than reading on real diffs is unmeasured. | R6 F5, F6, F25; R12 §7 open item | high for direction; transfer to SRE review UNVERIFIED |
| SR19 | The owner's real SRE-type failures (7 episodes): containers starting in the same second after a power cut, so a dependent came up before its dependencies; a restart claimed as the fix while the service stayed broken; a partial `pulumi up` (token created, secrets not written, 403); a fix committed but never pushed or deployed; nothing re-attaching receivers after PipeWire restarted; an unclosed lock file; and a hook failing with exit 127 in every session (`op: command not found`). These set the checklist order. | R16 §5 paranoid-sre table; R5 ep.4 | anecdotal, n=7 |
